# Profile 访谈

本文件由主流程在 Profile 构建阶段加载，负责图片分析、五个描述字段的起草、长期偏好访谈和 Gate0 语义复核。阶段进入条件、文件复制和 Profile 写入由 `SKILL.md` 负责。

## 目标

生成五段紧凑的自然语言描述，供其他 Agent 在多次视频任务中复用：

1. `character_description`
2. `scene_description`
3. `visual_defaults`
4. `presentation_defaults`
5. `staging_defaults`

设置这些字段是为了强制关注关键选择，而不是建立复杂的校验系统。

## 先检查，再提问

分别分析角色图和场景图。

角色描述应以自然语言涵盖主体类型、适用时呈现的性别与年龄、具有辨识度的外观、服装与配饰、主色调以及角色的艺术风格。将头发、头部特征、服装和配饰自然合并到一段描述中，不要拆成多个字段。遇到实质性歧义时应明确说明，不得自行编造确定结论。

场景描述应涵盖场所类型、具有辨识度的环境元素与布局、光线与主色调，以及场景的艺术风格或写实程度。只描述会影响角色调度或全息信息呈现的空间事实。

起草 `scene_description` 前，先独立完成一次可供性事实扫描，不受后续候选筛选结果影响。识别所有可能实质改变角色身体支撑、姿态性质、朝向关系、动作阶段或操作方式的高置信度可见结构属性，再决定如何紧凑地写入场景描述；不能因为某项调度尚未被选中，就提前忽略它的结构依据。

场景描述必须保留这些“可供性特征”，使用能够保存能力的名称或短语，例如可转向、可开启、可滑动、可调节、可依托或带有明确操作部件。不得把这类物件压缩成失去关键结构属性的泛化类别。图片不足以确认的属性只能作为待确认假设出现在访谈问题中；用户确认后，该属性可作为 Profile 事实写入 `scene_description`。`staging_defaults` 使用的独特能力所依赖的结构属性，必须能在 `scene_description` 中找到对应依据。

“提供依据”不等于“提前写结论”。`scene_description` 记录可见物件、结构属性、布局、空间关系，以及用户明确确认的长期结构属性；不描述角色将如何使用它们，也不写“讲解锚点”“操作区域”“状态切换区域”“轻松讲解区域”等调度判断。角色行为、能力组合和全息承载方式只写入 `staging_defaults`。

分别检查两张图片后，再结合二者起草 `staging_defaults`。它不是场景物件清单，而是当前角色与场景组合特有、可长期复用的调度能力描述。

先识别能力，再追溯物件。完整扫描场景能够提供的不同变化，包括角色姿态、身体朝向、讲解状态、动作阶段、互动方式、信息来源和全息承载关系，再确认这些能力分别由哪些可见物件或区域支持。不要先列出物件再为它们寻找动作；这种顺序容易让用途明显的信息设备压过需要进一步推理的姿态或状态变化。

按“新增调度价值”筛选，但比较单位是完整可观察配置，而不是动作动词。完整配置包括身体支撑方式、姿态性质、角色与锚点的朝向关系、活动状态、互动对象以及全息承载机制。两项调度都包含“坐下”或“站立”，不代表它们重复；只有完整配置基本相同，才视为缺少新增价值。候选扫描是为了避免遗漏，不是为了提高收录数量。普通换位、普通站立或指向，不会仅因依托物件不同就自动获得新的调度价值；如果某个对象本身是明确的信息载体、可操作设施或具有独特演示用途，则应描述它真正新增的能力。

对候选执行“移除锚点测试”：设想从场景中移除该锚点，判断原有完整配置能否继续保持，而不是只判断角色还能否完成同名动作。如果身体支撑方式、姿态性质、朝向关系、活动状态、互动对象或全息承载机制中有实质部分无法保留，该锚点仍具有独特价值。只有动作和完整配置都基本不变，全息信息也只是换一个位置悬浮时，才判定它不是场景提供的独特能力。普通转身、指向和手势属于角色在多数场景都能完成的通用动作，不能仅因朝向某个物件或区域就获得高价值。

筛选后再进行锚点簇合并。这里的“锚点簇”可以是一件核心物件，也可以是共同构成同一种调度方式的一组相邻物件。合并时必须保持能力保真：相邻物件可以分别贡献姿态或朝向变化、讲解状态切换、具体操作、信息来源与全息承载区域，合并后的自然语言必须保留这些互不重复的能力。不得让语义更明显的设备操作覆盖同一锚点簇中的姿态、朝向或状态变化。

对最终描述中每个明确写出的物件，检查促使它入选的独特能力是否得到体现。每个保留物件都应贡献不可替代的调度能力；行为措辞不同不代表锚点不同，只有角色需要转移到实质不同的空间关系，或者新的对象提供独立能力时，才保留为另一个锚点。

姿态、朝向或讲解状态变化只是可选的高价值能力之一，不是每个锚点必须包含的组成。只有图片明确支持、变化确实由锚点造成、能够在安全构图内完成，并且相对于已选能力带来新增价值时才采用。稳定的坐姿、依托姿态、操作状态或手势互动本身也可以构成有效调度；不得为了展示方法论而虚构准备、阅读、思考、起身或其他过程。

确实采用状态变化时，必须用可观察的过程表达：写清起始状态、由锚点支持的连接动作和结束状态。优先描述角色相对于场景锚点的关系如何变化，不使用“固定正面”“固定侧面”等通用机位结论代替调度关系。不得在最终描述中只写“改变朝向”“状态切换”“动作变化”等抽象标签；无法说明起点、过程和终点时，不把它计为独特调度能力。

不要把调度能力、支持物件和全息承载关系彼此割裂地罗列。每个保留的锚点都必须说明它能够支持的具体角色行为、全息承载方式，或二者同时说明，形成“场景锚点 → 角色行为 → 全息信息如何依托该锚点出现”的自然语言关系。

动作必须与图中物件的可见结构和通常用途相符；无法高置信度判断某种操作能力时，改用指向、展示或依托等可信动作，不得擅自假定隐藏功能。动作对象应写成图片中可辨认的具体物件，不得用含糊的“设备区域”“设施附近”等称呼掩盖无法确定的操作对象；空间区域仍可用于描述全息信息出现的位置。

从调度建议整理最终字段时，保持动作对象和物理含义不变。对一个表面做手势、操作一个可见控件、触碰一个屏幕是三种不同能力，不能为了让句子更顺而互相替换；只有图片或用户确认明确支持时，才能改变动作对象或操作方式。

只保留画面中明确可见或能够高置信度判断的空间关系，优先选择少量真正有用的锚点，不要罗列家具和装饰品清单。记录正向可能性，不要写成长篇限制说明。

`staging_defaults` 不描述要展示的通用知识内容，例如模型、图表、流程、概念或重点信息，也不重复 `visual_defaults` 中的全息视觉风格；它只描述全息信息可以依托哪个场景区域出现，以及角色如何使用该锚点。只有当信息类型是某个可见设备或锚点自然产生的固有输出时，才可具体说明，例如仪器读数。其余情况统一使用“全息信息”或“全息信息层”等中性称呼，把具体知识形态留到 Gate2 根据本次内容决定。

不得加入通用镜头语言、角色在画面中的左右位置、通用朝向、安全景别、普通站立讲解或固定分镜方案。也不得预先规定全息信息的大小、远近、画面占比或其他单个分镜才需要决定的尺度属性。普通站立在每次视频任务中始终可用，无需写入该字段；只有当场景存在能够实质改变调度方式的特殊站立锚点时，才描述与站立有关的内容。

虽然不把景别规则写入 `staging_defaults`，但必须用后续安全构图反向筛选每项调度可能：角色动作、互动手势和主要全息承载区域应能同时清晰出现，不能依赖稳定构图中通常不可见的身体部位或低位场景空间，也不能要求相机为了容纳承载位置而拉远。承载位置优先相对于可见场景锚点描述；没有合适的锚点表面时，可使用角色手边或锚点附近稳定可见的前景、中景空间。最终自然语言只保留筛选后的正向调度关系，不写入这段检查过程。

## Few-shot 判断示例

这些例子用于说明筛选方法，不是固定物件清单，也不得替代对当前图片的判断。

### 示例一：用移除锚点测试排除通用动作

某户外广场中可见一块静态景观石和空闲区域。若候选只是让角色转身指向景观石，并让全息信息悬浮在旁边，移除景观石后动作和信息呈现方式仍基本不变，因此它不是场景提供的独特调度能力。

应删除的写法：

> 景观石可作为展示锚点：角色可转身指向该区域，让全息信息在旁边展开。

### 示例二：保留朝向与讲解状态变化

某天文观测环境中可见一台可转向观测仪、固定标牌和空闲角落。`scene_description` 应保留“可转向”这一高置信度结构属性，而不是泛化成“观测设备”。观测仪的价值不只在于可操作，还在于它能让角色先侧身进入观测状态，再调整仪器方向并切回讲解状态；其余两处如果只能支持换位指向，就不应单独收录。

保留结果可以是：

> 可转向观测仪可作为状态变化锚点：角色可侧身调整仪器方向，再从观测状态转回讲解，让观测轨迹从仪器附近展开为全息信息。

### 示例三：区分可信操作与模糊推断

某录音环境中可见带推子的调音台、话筒和吸音结构。角色可以操作清楚可见的推子，并让设备产生的电平信息在控制面上方展开；不能因为某片区域看起来像电子设施，就假定它支持触控或其他不可见功能。吸音结构如果只能充当角色身后的装饰，也不构成独立锚点。

保留结果可以是：

> 调音台可作为操作式讲解锚点：角色可推动可见推子，让对应的电平信息从控制面上方展开为全息信息层。

### 示例四：合并时保留互补能力

某文物修复环境中，可摆动放大镜与样本托盘共同组成一个演示区域。两者不应拆成两个锚点：放大镜贡献角色俯身细看、再抬头切回讲解的状态变化，样本托盘贡献观察对象和全息信息承载区域。合并时不能只保留“查看样本”，否则会丢失放大镜带来的姿态与状态变化。

合并结果可以是：

> 可摆动放大镜与样本托盘组成修复演示锚点：角色可将放大镜移向样本，俯身进入细看状态，再抬头切回讲解，让观察标记从托盘上方展开为全息信息。

### 应删除的泛化写法

> 角色可在场景中以半身景别展示概念、流程和重点内容。

这段内容只包含普通站立、通用景别和通用知识类型，几乎可以原样用于任何室内场景，因此不应写入 `staging_defaults`。

起草后进行一次语义复核：

1. 对照独立完成的可供性事实扫描，确认没有因为候选尚未入选而遗漏可能改变身体支撑、姿态性质、朝向关系或操作方式的高置信度结构属性，同时没有把“完整扫描”误解为“尽量收录”。
2. 检查 `scene_description` 是否保留了所选能力依赖的结构属性；图片明确支持时直接记录，图片无法确认时必须有用户明确确认，否则删除该能力。字段中只保留图片事实、用户确认的长期结构属性及其空间关系，不写角色行为、锚点分组、操作区域和状态切换等调度结论。
3. 以完整可观察配置比较每项能力的新增调度价值，并执行移除锚点测试；不得仅因动作动词相同就去重，也不得只更换物件名称却保留基本相同的配置。
4. 逐句判断它是否依赖画面中明确存在的特定锚点，是否说明具体能力或承载关系，以及它能否不经修改就套用到大多数其他场景；删除可以通用于大多数场景的句子。
5. 删除不属于可见锚点固有输出的通用知识类型，以及大小、远近、景别、画面占比等应在 Gate2 决定的词语。
6. 复核每个动作是否确实由图片支持，动作对象是否具体；把依赖不确定功能的操作改成更可信的行为。
7. 比较所有保留项的核心物件、主要空间位置和全息承载区域；如果高度重合，将它们合并为一个锚点簇。
8. 对每个锚点簇执行能力保真检查：每个明确写出的物件都应贡献已写出的独特能力，合并后的描述应覆盖所有非重复能力，不保留没有独立贡献的物件名称。
9. 检查是否为了让每个锚点都有变化而强行设计过程；没有必要或缺少依据时选择稳定姿态、可信操作或手势互动。确实保留状态变化时，再检查是否明确写出起始状态、锚点支持的连接动作和结束状态，排除只有抽象标签的伪变化。
10. 在不扩大安全构图的前提下，检查角色动作、互动手势和主要全息承载区域能否同时清晰可见；不能满足时，改用锚点附近稳定可见的承载区域。
11. 对照用户确认的长期调度方案，确认最终字段没有丢失或替换关键结构属性、动作对象、完整可观察配置、因果动作和全息承载关系；措辞可以压缩，语义不得漂移。

该复核只用于改进自然语言描述，不增加任何结构化字段或校验脚本。

在询问用户之前，先根据图片起草 `character_description`、`scene_description` 和长期场景调度建议。识别图片事实和可信调度可能是 Agent 的责任，不要要求用户描述能够直接从图片中检查的信息。

## 以小型设计树进行访谈

分轮进行访谈。每个尚未确定、会长期生效的决策都是一条分支；当前前沿由所有前置决策已经确定、现在即可回答的问题组成。每轮一次性询问当前前沿的全部问题，为问题编号并给出推荐答案，然后等待用户回答，再继续处理依赖这些答案的后续问题。

保持设计树精简，只询问会实质影响后续多次视频制作的长期决策，通常包括：

- 常见的知识或讲解内容类型。
- 长期使用的讲解语气。
- 对类比、故事、提问引导或直接讲解方式的偏好。
- 常用语速，以及表情和手势的强度。
- 全息视觉语言，例如科技、魔法、可爱、克制或用户定义的其他方向。
- 当角色与场景风格不一致时，二者应如何共存。

此外，每次首次建立或重新设计 Profile 时，都必须加入一个“长期场景调度方案”确认问题。这个问题不是让用户识别图片，而是由 Agent 根据完整可观察配置先给出动态推荐：用一两句话列出建议保留的少量锚点簇、各自不可替代的姿态或活动配置、以及全息信息如何依托它们出现；同时说明普通站立始终可用，只有普通换位价值的弱候选不会写入 Profile。若图片只支持一个高价值锚点，就如实只推荐一个，不得为了让选项丰富而虚构第二个。完整调度推荐只在这个编号问题中出现一次；访谈前言只展示角色与场景的图片事实。

推荐依赖某项对长期调度很重要、但无法仅凭图片高置信度确认的结构属性时，在问题中把它明确写成待用户确认的假设，不得悄悄当成图片事实。用户确认后，该属性就成为已确认的 Profile 知识，最终 `scene_description` 必须保留其结构依据，`staging_defaults` 必须保留相应能力及因果关系。

问题可以采用以下自然语言形式，具体内容必须随当前图片变化：

> 长期场景调度方案：推荐保留“<锚点簇与完整配置 A>；<锚点簇与完整配置 B>”，普通站立讲解仍可随时使用，其他仅提供普通换位的区域不写入 Profile。是否按此方案，或希望增删、调整其中某项？

推荐中不得写通用机位、固定分镜或本期知识内容。用户回复“全部按推荐”时，视为同时确认这一调度方案；用户提出调整时，只修改相关调度能力，不要求用户重新描述图片事实。
访谈前言只展示角色与场景事实；完整调度建议集中写入“长期场景调度方案”编号问题，并且只出现一次。

问题中“普通站立仍可用”、被排除的弱候选及筛选理由属于访谈解释层，只帮助用户理解推荐。最终 `staging_defaults` 只保存用户确认的正向锚点簇、角色行为和全息承载关系，不得复制这些解释，也不得加入通用兜底规则。

不要把目标受众、知识深度、目标时长或一次性特殊要求固定到 Profile 中，这些信息属于单次视频任务。不要重复询问已经能够从用户请求中明确得到答案的问题。

## Gate0

将已经确定的长期决策整理为一段 `visual_defaults` 和一段 `presentation_defaults`。把全部五段最终描述与两张图片的复制目标路径一起展示给用户。

用户确认的长期场景调度方案是最终字段的语义契约：可以合并重复措辞，但不得为了简洁改变动作对象、物理含义、关键结构属性、完整可观察配置或全息信息的来源与承载位置。最终展示前，逐项对照确认过的方案检查语义保真。

等待用户明确确认，只修改用户要求调整的内容。确认后把五个最终描述字段交还主流程持久化。
